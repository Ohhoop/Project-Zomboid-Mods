Summary

Starting new games one after another in a single client session leaks roughly 25 MB of Java heap per world. Nothing of that 25 MB is ever reclaimed.

With the default -Xmx3072m the process eventually runs out of heap and the game stops responding. On my machine it takes between 17 new worlds (extreme settings) and 42 (standard apo), depending on sandbox settings.

If you take a heap dump at any point, the clearest symptom is the zombie.characters.IsoPlayer count. It matches the number of worlds loaded since launch, one for one. Forty-two worlds, forty-two players still in memory, forty-one of them belonging to games that ended long ago. Same for GameTime, ClimateManager, ScriptModule and the rest of the per-game objects.

I spent a while chasing this and ended up with three separate causes, plus a small fourth one in a vanilla Lua file. I am not confident I read the bytecode correctly everywhere, so the code-level parts below are leads rather than conclusions.

Tested on 42.20.2 (ffe7a8a4b1), Steam build 24574865, public branch, Windows 10 19045, bundled Zulu JRE 25.0.1+8-LTS, ZGC, default -Xmx3072m.

Reproduction

  1. Launch the game.
  2. Create or load a world.
  3. Quit to the main menu.
  4. Repeat from step 2.


For a long stretch nothing looks wrong, every world loads in about 5 seconds. Near the end the loads start dragging, 10 seconds, then 30, then 75, and on the next one it just never finishes. The window stays up, no error box, nothing in the logs past the middle of the load. Event Viewer records it as an Application Hang.

The rate depends heavily on sandbox settings, because one of the three causes scales with the number of characters spawned rather than with the number of worlds. A high zombie population reaches the ceiling in 6 to 9 worlds instead of 40.

How I measured it

I ran the game outside Steam with GC logging enabled:

-Xlog:gc*:file=gc.log:time,uptime -XX:+HeapDumpOnOutOfMemoryError


For each world loaded I took the minimum post-collection occupancy across the major ZGC collections in that world's time window. That gives the live set once the transient loading allocations are gone. A linear regression on that series gives the leak rate.

I used only major collections, since minor ones do not reclaim the old generation and their post-collection figure is not a live set.

Three separate sessions:

SessionWorldsSlopeStandard error
A42+24.8 MB per world1.6
B41+28.5 MB per world1.6
C16+19.8 MB per world9.6


One caveat worth flagging so nobody wastes time on it: the High column in the ZGC heap statistics saturates at 3072 MB on nearly every world load, including in sessions that never crashed. It is not a usable peak measurement here.

I then took the heap dumps written at OOM, 3.3 to 3.5 GB each, and analysed them with Eclipse MAT 1.17, mostly the dominator tree and the leak suspects report. I cross-checked the object counts and the reference chains with my own HPROF parser so I was not relying on a single tool, and finally disassembled the shipped projectzomboid.jar to check the mechanisms in the bytecode.

All three dumps produce the same leak suspect at the top, with the same retention path.

Culprit 1: the root AnimLayer of every character is never returned to its pool

This is by far the biggest one: 1,085,159,336 bytes, 32.67% of the heap, in the 42-world dump.

What the heap shows

MAT reports a single zombie.util.Pool$PoolStacks instance retaining just over a gigabyte. The shortest path to the accumulation point is:

MainThread
  -> java.lang.ThreadLocal$ThreadLocalMap
    -> zombie.util.Pool$PoolStacks
      -> inUse   gnu.trove.set.hash.THashSet
        -> _set  java.lang.Object[51437]
          -> 13,253 AnimLayer
            -> AnimLayer.character


Breaking that retained size down by class, 13,253 AnimLayer account for 1,076,329,648 bytes of it, which is 99.19%. That works out to about 81 KB retained per layer, because each one still points at a full character through its character field.

There are 57 Pool$PoolStacks instances in the heap. Every one of them recycles normally except this one. Contents in the 15-world dump:

0x40000e30f4013,8970AnimLayer

The AnimLayer pool has never had a single object returned to it. Counts line up one to one with characters ever created: 14,180 AnimLayer and 14,180 AdvancedAnimator for 14,049 characters in the 42-world dump. That is 13,814 zombies, 42 players, 42 survivors and 151 animals.

The strongest single piece of evidence is this. AnimLayer.onReleased() sets character to null unconditionally, and I checked every AnimLayer in both dumps, 28,104 objects. Not one has a null character. No layer has ever been released in the entire lifetime of either process.

What I think is happening in the code

zombie.util.Pool keeps its stacks in a ThreadLocal. Pool.alloc() adds to PoolStacks.inUse, and Pool.releaseItemInternal() removes from inUse, adds to released and calls onReleased(). Leaving inUse requires a release, there is no other path.

AnimLayer extends PooledObject and allocates from a private static final s_pool created in its <clinit>. AdvancedAnimator.init() takes the root layer from that pool.

Sub-layers are handled correctly. SubLayerSlot.reset() calls Pool.tryRelease(this.animLayer), and AdvancedAnimator.cleanUpEmptyLayers(List) releases inactive slots. The root layer is the one that never comes back.

AdvancedAnimator has no dispose, destroy, free or release method at all. I went through all of its methods looking for one.

What made me fairly confident is IsoGameCharacter.removeFromWorld(), which is short enough to quote in full. Bytecode offsets from the shipped jar, I do not have source line numbers for this one:

   0: getstatic     zombie/network/GameServer.server:Z
   7: invokestatic  zombie/iso/objects/IsoFireManager.deleteCharacterOnFire
  11: invokespecial zombie/iso/IsoMovingObject.removeFromWorld
  15: invokevirtual zombie/characters/IsoGameCharacter.releaseRagdollController
  19: invokevirtual zombie/characters/IsoGameCharacter.releaseBallisticsController
  23: invokevirtual zombie/characters/IsoGameCharacter.releaseBallisticsTarget
  27: invokevirtual zombie/characters/IsoGameCharacter.closeAnimationRecorder
  44: invokevirtual zombie/characters/NetworkCharacterAI.resetState
  51: invokevirtual zombie/characters/IsoGameCharacter.removeOnFireLightSource
  54: return


Three pooled resources are given back there: the ragdoll controller, the ballistics controller and the ballistics target. The animator's root layer is not, and neither is the AnimationPlayer.

The idiom already exists one method away, in the same class:

IsoGameCharacter.releaseAnimationPlayer()
   this.animPlayer = (AnimationPlayer) zombie.util.Pool.tryRelease(this.animPlayer);


So a fix would presumably look like the same one-liner on AdvancedAnimator.rootLayer, called when the character or its StateMachineComponent is torn down. Based on the dominator tree that alone would free 715,959,720 bytes out of the 719,835,128 the pool holds in the 15-world dump, so 99.46%.

One thing I got wrong at first

The object graph here contains a cycle. Every pooled object holds a Pool$PoolReference whose poolStacks field points back at the PoolStacks, so a live character reaches the pool through its own root layer. I checked this on a real object: IsoZombie at 0x40000b9d4f0 reaches the pool through ecsComponentMap, then StateMachineComponent.advancedAnimator, then rootLayer, then pool, then poolStacks.

That cycle does not save the stale characters, since a tracing collector only keeps a cycle alive if a root enters it. MAT's own numbers confirm the split: of the 13,924 layers in inUse, only 8,272 are dominated by the pool. The other 5,652 belong to the current world and are reachable from IsoCell as well.

Worth noting that detaching a character from the world is not enough on its own. In the 15-world dump IsoCell.instance.zombieList holds 3,864 zombies out of the 13,540 in the heap, so 9,676 of them are no longer attached to any cell and are still fully alive in memory. Nothing on the removal path touches the animator, so the layer keeps its character reference and the pool keeps the layer.

Culprit 2: TileDepthTextureAssignmentManager re-reads the assignment file on every world exit and keeps every copy

305,942,512 bytes in the 42-world dump, 9.20% of the heap. It is also 89% of everything retained by static fields in the whole game.

The class

zombie.tileDepth.TileDepthTextureAssignmentManager is a singleton. instance is private static (access flags 0x000a) and modData is a private final instance field (0x0012), an ArrayList.

It has 13 methods: getInstance, <init>, init, initGameData, initModData, save, getModData, initSprites, assignTileName, two overloads of getAssignedTileName, clearAssignedTileName, assignDepthTextureToSprite.

Across the whole class there are exactly two operations on that list, both ArrayList.add:

initGameData()   offset 28: invokevirtual java/util/ArrayList.add
initModData(Mod) offset 37: invokevirtual java/util/ArrayList.add


There is no clear, no remove, no set, and no Reset method anywhere in the class.

The comparison that convinced me

init() is called from three places: GameWindow.initShared() at offset 226, Core.ResetLua(String,String) at offset 294, and IngameState.exit() at offset 1264. Here is the relevant stretch of IngameState.exit() itself:

1058: invokevirtual zombie/tileDepth/TileGeometryManager.Reset
1064: invokevirtual zombie/tileDepth/TileDepthTextureManager.Reset
      (nothing for TileDepthTextureAssignmentManager, it has no Reset)
1258: invokevirtual zombie/tileDepth/TileGeometryManager.init
1264: invokevirtual zombie/tileDepth/TileDepthTextureAssignmentManager.init
1270: invokevirtual zombie/tileDepth/TileDepthTextureManager.init


Three managers built on the same pattern: singleton with an ArrayList modData, init(), initGameData(), initModData(Mod) and an inner ModData class. Two of them are reset, the third is not. Core.ResetLua() repeats the same shape.

TileDepthTextureManager.Reset() migrates its entries into previouslyLoadedModData and then calls modData.clear() at offset 55, and its initGameData() looks the existing entry up before creating a new one. TileGeometryManager.Reset() calls modData.clear() at offset 41.

The result in a single heap dump, same process, same lifecycle, after 15 worlds:

ManagerHas Reset()ModData instances
TileGeometryManageryes1
TileDepthTextureManageryes1
TileDepthTextureAssignmentManagerno15


Entry counts across the three dumps: 15 entries after 15 worlds, 41 after 41, 42 after 42. The backing array is Object[49] in both of the larger ones, which is just the next ArrayList growth step.

What each entry costs

Every entry is a full re-read of the same file. All 42 ModData in the 42-world dump share the same interned modId object, the literal "game", while their mediaAbsPath values are 42 distinct String objects with identical content, which is what you get from 42 separate calls to getMediaRootPath().

Each one carries a HashMap with 31,670 entries, and media/tileDepthTextureAssignments.txt is 1,750,760 bytes over 31,673 lines, which is 31,669 key/value pairs plus the VERSION line. That comes to 7,284,345 bytes per entry, stable to within a few bytes between the 15-world and the 42-world dump.

The retention cascade is manager 305,942,512, the 42 ModData 305,941,888, the 42 TileDepthTextureAssignments 305,936,528. So 99.998% of it is the assignment tables.

Note that 7.28 MB is a floor rather than a fixed cost. initGameData() adds the game entry unconditionally and initModData(Mod) adds one per mod that ships a tileDepthTextureAssignments.txt, so anyone running tile mods loses more than that per world.

There is a CPU side to this as well

getAssignedTileName(String), the single-argument overload, walks the list and returns the first non-null result rather than the first matching entry:

 2: iload_2 / size() / if_icmpge -> 49
18: modData.get(i).assignments.getAssignedTileName(name)
37: ifnull -> 43   (iinc, goto 2)
42: areturn
49: aconst_null


On a lookup miss it therefore probes all 42 copies. Its caller initSprites() iterates IsoSpriteManager.namedMap.values() and calls it for every sprite without a depth texture, on every load, so the cost grows with the number of worlds played.

save(String) goes through getModData(modId) and only ever writes the first match, so as far as I can tell there is no risk of the duplicates being written back to disk.

Possible fixes

In increasing order of niceness: add a Reset() that calls modData.clear() and call it next to the other two at offset 1064, or reuse the existing entry the way TileDepthTextureManager.initGameData() already does with previouslyLoadedModData, since the parsed content is identical every time.

One detail that may matter for pinning down the exact trigger. With three call sites you would expect N+1 entries after N worlds if startup contributed one. I see exactly N in all three dumps, which fits "one at startup, one per world exit" with the dump being taken during the load of the Nth world. That would also mean Core.ResetLua() did not fire in these sessions.

Culprit 3: Item.netIdToItem keeps stale network id mappings

Smaller, roughly 245 KB per world, but it is exactly linear and it never stops. zombie.scripting.objects.Item.netIdToItem is a static map. Entry counts:

DumpWorldsEntriesPer world
C1576,5755,105.0
B41209,3055,105.0

The rate is identical to one decimal place across three independent sessions.

The saving grace is that the Item objects themselves are not accumulating. There are only 6,130 Item instances in the 42-world dump against 214,410 entries, so it is the mappings that pile up, roughly 35 stale ids per item. The cost is the map nodes and the boxed keys rather than the values.

Minor: duplicate appends in media/lua/shared/Moveables/ISMoveableSpriteProps.lua

Not a memory problem, a few bytes, but it is a one-line fix and it makes a handy diagnostic. Lines 1 and 2 of that file are:

IsoGridSquare.ignoreBlockingSprites:add("constructedobjects_signs_01_11")
IsoGridSquare.ignoreBlockingSprites:add("constructedobjects_signs_01_27")


They run at file scope, so they execute again every time the Lua environment is reloaded, with no check for an existing entry. IsoGridSquare.ignoreBlockingSprites is public static final and nothing on the Java side ever adds to it or clears it, so the list grows by two per world: 30 entries after 15 worlds, 82 after 41, 84 after 42.

The strings are interned so the memory cost is negligible, and contains compares references, so the CPU cost is negligible too. Worth mentioning mainly because the two-per-world growth tracks the TileDepthTextureAssignmentManager entries exactly, which is how I confirmed the two share a trigger.

Worth noting for anyone setting the default heap size: about 1.7 GB of the 3 GB is engine data that does not vary with the number of worlds. Between that and the 600 to 900 MB transient peak during a world load, there is not much headroom left for anything that accumulates.

What I could not work out

There is a second failure mode I have not explained, and I am not claiming it is related. In 8 of 9 sessions the game stopped responding with the heap only 55% to 96% full and no OutOfMemoryError at all. Zero CPU, all 109 threads parked in kernel waits, no growth in handles or thread count, no FMOD or OpenGL errors.

Private bytes peaked at 5.1 GB and were at 4.4 GB when it hung, on a 32 GB machine. The main game thread's instruction pointer was inside the JIT code cache rather than any loaded module. I took a minidump of one of the hung processes but without symbols I could not get further than "everything is waiting on something".

The one session that did hang on heap exhaustion ended on twelve consecutive major collections at 3072M(100%)->3072M(100%), all triggered by allocation stalls, reclaiming nothing, with no OutOfMemoryError ever thrown. That may be worth a look on its own.
